## Implementation (APK, code quality)

We evaluated your APK’s functionality, stability, and user experience, along with the quality and consistency of your code. We also reviewed your CI setup, Sonar integration, and tests, including the presence of at least two meaningful end-to-end tests and the line coverage achieved.

The APK still has several issues. The logo appears slightly blurry on the login screen, and tapping “Forgot password” causes the app to crash. Sign-in with Google is also non-functional. Skill tags currently use underscores instead of spaces, which is not very user-friendly. On the “My Skills” page in the profile, adding a visible back button would improve navigation, even if Android gestures work. Profile name changes have no validation, and creating a post produces unclear error messages such as “Failed to add post M689YEBFfnrg69” when invalid tags are entered. It is also impossible to view “My Posts,” and post creation lacks basic validation, for example, titles can be extremely long. The feed is currently unusable, and although the chat UI looks good, it is not connected and cannot be used.

Regarding code quality, the overall code is solid, but there is a surprisingly large number of classes and files given the limited set of features, which raises questions about the overall architecture and whether it was planned sufficiently in advance. The organization is generally good, but the code does not consistently follow MVVM or standard naming conventions. Ideally, the repository interface should be named FeatureNameRepository and its implementation FeatureNameRepositoryImpl. The ViewModel should follow FeatureNameViewModel, UI components should be named FeatureNameFragment or FeatureNameScreen, and optional supporting classes should follow FeatureNameUiState and FeatureNameEvent for state and user actions.

Some SonarCloud issues remain open, including 4 high-priority items that should be addressed, along with 21 medium-priority ones that would be worth reducing even if not all are critical. Overall, the code quality is good and moving in the right direction, but you should resolve theses. However you have 0% of code duplication, which is very good.

As for tests and CI, the code coverage and CI pipeline are very good. However, there is only one end-to-end test for M1 and none for M2, which leaves significant functional paths untested.

For this part, you received 4.06 points out of a maximum of 6.

## Figma and Architecture Diagram

We evaluated whether your Figma and architecture diagram accurately reflect the current implementation of the app and how well they align with the app's functionality and structure. 

Overall, the Figma is clean, and the screens look nice! A few UI parts in the Figma are ahead of the current app, which is good, for example both the feed and chat screens. Some screens are organized by user flow; however, the user flow isn’t properly documented or named in Figma. Another important point is to name each screen as well, which hasn’t been done yet.

You delivered a UML diagram for M2, not an architecture diagram that clearly follows the Android App Architecture Guide. The diagram is supposed to be a high level representation of your app, where we can clearly see the relationships between the UI layer, domain layer, and data layer. You already received this feedback for M1 and haven’t taken action to fix it. In addition, the UML diagram is not up to date with the current state of your app, for example the Message data model is missing.

For this part, you received 3.25 points out of a maximum of 6.

## Sprint Backlog & Product Backlog

We assessed the structure and clarity of your Sprint and Product Backlogs and how you used them. We looked at whether your tasks are well defined, appropriately sized, and aligned with user stories; whether the Product Backlog is well organized and value-driven; and whether the Sprint Backlog is continuously updated and demonstrates good planning and prioritization.

The Sprint Backlog and Product Backlog are well constructed, and you have many user stories ready for future work. They are clearly improved compared to M1.

For the estimated time, you linked it to the label size. While that works, it would still be better to use the dedicated field you already have, because the size of an issue is not always proportional to the time required to resolve it.

However, the main issue is the absence of the “actual time” field for all tasks, despite this being explicitly required in the instructions. Additionally, labels such as user story, epic, and task, as well as dependencies between issues, are not used consistently. Every issue should have a clear relationship to others and must always be linked to a corresponding user story or epic.

You are also still using the labels “S4, S5, S6,” even though we already asked you to stop doing that. If you really want to link a task to a specific sprint—something that should normally be handled by the “Done in S…” column—you may add an “iteration” tag. However, this should definitely not be done through labels.

Overall it’s good, but not very consistent.

For this part, you received 5 points out of a maximum of 6.

## Scrum Process (documents, autonomy)

We evaluated your ability to autonomously run and document the Scrum process. We looked at how well you documented your team Stand-Ups and Retrospectives for each Sprint. We also assessed your level of autonomy in organizing and conducting these ceremonies, defining and prioritizing user stories in your Product Backlog, and planning well-scoped Sprint tasks that lead to concrete, valuable increments.

All your Scrum documents were fully completed before the meeting. Meetings also consistently start on time, and both the SM and PO provide relevant input. However, the meetings could be a bit more structured, and the SM should be the one leading and guiding them. You generally demonstrate good autonomy during the meetings, but sometimes the correct order is not followed. For example, the demo does not always occur at the beginning of the meeting, or sometimes you move directly to the sprint retrospective and do the sprint review afterward. For M3, the ceremony process should be clear, and the meetings should be fully managed by you.

For this part, you received 5 points out of a maximum of 6.
